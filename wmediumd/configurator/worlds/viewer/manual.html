Start with the mode badge. A convincing animation is not proof of a live connection, a successful roam, or a healthy network.

1. Quick start

In the live network topology, hover an extender or Agent-1 for AP-reported BSS load: channel utilization in percent and raw 0–255, associated stations per BSS, band/channel and report age. Interactive rooms collect these reports passively, without enabling load steering. Stale or missing values are unavailable, not zero. This is not a beacon capture; BSSs sharing a radio do not have independent utilization budgets.

The RF inspector, topology and Console NG use the same property catalog and independent passive observations. Candidate collection or steering failures do not freeze native load. Unknown radio/channel context stays unverified; configured stimulus is not measured evidence. The read-only /api/demo/rf-catalog and /api/demo/rf-observations endpoints expose units, source, timestamps and validity without requesting new scans. Console NG includes an RF properties manual explaining each simulation and observation path; it does not add RF controls.

Try the room without a lab

  1. Open the public sandbox. Look for NO CONNECT; no mode parameter is needed.
  2. Select a client, drag it across the floor, and release it. No pointer-mode switch is needed.
  3. Read the movable details panel: coordinates, walls, predicted SNR, and the modeled strongest AP. Drag its dark background to move the panel without moving the device.
  4. Try Move to…, then click a destination. Drag empty space to orbit, or Shift-drag anywhere to pan.
  5. Select Reset role or Reset all to clear your preview edits.

Operate the live lab

  1. Open the rev150 prplMesh 0913 live room from a network that can reach the lab. Interactive control is the server default; no mode parameter is needed.
  2. Wait for live state and current controller telemetry. Check the Whole lab card before editing.
  3. Drag a device or press Play. No operator token is required; the browser acquires a control lease automatically. Another browser may already hold control.
  4. Confirm the LIVE RF badge, then drag one role and release it.
  5. Wait for the accepted RF event, fresh measurements, and the optimizer result. The actual association line changes only when controller evidence changes.

The current room name appears at the top of the room and network topology, including fullscreen. It updates when a room loads, even with manual topology layout. If room data becomes unavailable, the topology marks its previous room name as last observed.

Drag the grey divider between the left panel and the room/topology to give the drawing more space. Each view remembers its width in your browser. Focus the divider and use Left/Right arrows (Shift for larger steps), Home/End for the width limits, or double-click to reset. On narrow mobile screens the panels remain stacked; fullscreen shows only the drawing view.

Opening this manual does not pause the room, stop a walk, acquire control, or change RF. Live measurements and an already authorized optimizer continue while you read. Close the manual with its Close button or Esc.

3. Reading the screen

  • Left sidebar: mode, run ID, live cards, world and time controls, band selection, interaction controls, and the selected-node link table. Scroll it to reach lower controls.
  • Room drawing: the floor, walls, mesh nodes, clients, paths, and link overlays. These positions define the experiment's geometry.
  • Movable properties panel: starts in the upper-right when inspecting a client or mesh node. Grab its dark background and drag it anywhere in the viewport; this changes no RF or device position and needs no control lease. Placement stays local to your browser and is remembered across selections and reloads. The panel stays within the visible window when resized. Double-click its heading or press Home while it is focused to reset. Arrow keys move it by 10 pixels; Shift+arrow moves one pixel.
  • Whole lab: device/client counts, private and IoT cohorts, observed topology shape, and health. The normal 20-client profile expects 10 private and 10 IoT clients.
  • Traffic probe: Ctrl-click any client (⌘-click on Mac). The right-click menu also has Use as traffic probe. A cyan outer ring marks this shared probe; the separate yellow ring marks optimizer focus. Client body colors stay unchanged. The default is sta_mobile_01, using its ordinary client label. Selection requires the interactive control lease, changes no RF/position/presence, and is visible to observers. Offline clients pause their probe; reconnection resumes it. The probe stays selected across world loads and resets to the default on a new server session. Fleet reconciliation still considers all active clients; the probe has no special steering privilege and is not a check of every client's traffic. Older evidence can retain the legacy hero alias.
  • External optimizer: authority, policy reason, current focus, fleet coverage, stronger candidates, rolling request window, paused clients, and the last verified outcome.
  • RF inspector: select an AP or client, then open the inspector. Local AP Metrics are separate from client-heard BSS Load advertisements: BSSID/channel, receiver, source, scan identity and age identify the evidence. AP selection includes neighbors heard by its clients and advertisements of that AP heard elsewhere. Scans expire after two seconds; the inspector never initiates scans. AP TX retries/failures and RX drops retain direction and freshness; lost ACKs can cause failures despite delivery. Configured stimulus and optimizer decisions stay separate. Traffic experiment distinguishes offered UDP rate, actual sender traffic, receiver goodput and loss. Zero is valid; missing or stale is not zero.
  • Recent events: a short running narrative. Live entries show actual age (for example, 12s ago), independent of paused playback or its four-minute endpoint. Hover over the age for the recorded timestamp. Replay entries retain scenario time. Full details and earlier events live in the saved evidence.

The healthy model shorthand 5/15/50/24 means five mesh devices, fifteen radios, fifty BSS entries, and twenty-four associations, including backhaul, in the RDK model. prplMesh has its own native BSS inventory; its health card counts five physical mesh devices. The WebUI may draw a separate Controller node alongside Agent-1, so six displayed icons do not imply six physical mesh devices.

Apply a different live world

World is the first control section in the left panel, above live status and optimizer readings. Choose the room here to set its geometry, active clients, RF inputs and backhaul policy; the room browser, local-file loader and default-room restore are grouped with it.

On an updated interactive server, selecting a world or opening a local .world.json immediately applies it to the lab. There is no separate Apply button, confirmation, or operator-token prompt. The control lease and current revision still protect the operation. World controls are disabled while loading. The displayed room changes only after server acceptance; invalid uploads or denied control retain the current room and show an error. Stop and download an active recording first.

The fixed pool stays running: 100 client containers and five mesh containers, represented by six mesh topology nodes. A 12-client world isolates the 88 unused clients on all serving radio links; no containers are created, stopped or deleted. Health expectations follow the online subset. The native topology reports actual associations, so wait for its count to converge rather than expecting an instant display filter.

The steering policy also follows the requested online count. Client roster ready only confirms appearance/disappearance and lab health; check the optimizer for AP convergence. Ordinary clients retain same-network, same-band policy; explicitly profiled band-room clients also compare permitted bands. Convergence means the configured policy is satisfied, not necessarily maximum signal. A healthy ten-client count alone does not mean those ten clients have finished roaming.

Browse rooms · RF & optimizer guide opens a room-selection dialog with detailed guidance for every bundled room. Hover, keyboard-focus or tap a room to read its simulated RF inputs, expected optimizer behavior, checks in the room and Network Topology, and what it cannot prove. Use the arrow keys within the list; Escape closes the guide. Browsing never changes the lab. Load room uses the normal immediate live-load flow; Load preview in the no-connect sandbox changes geometry only. Observer/replay views remain read-only. The original quick selector stays available, with native tooltips where supported. Custom uploads receive a generic explanation, not invented expectations.

The guide’s Shared RF model & proof boundaries explains directed SNR, distance/walls, per-band loss, the fixed noise reference and synthetic candidate RCPI. Expected checks are not recorded PASS results: confirm fresh native BSSID/frequency, controller ownership and traffic alongside optimizer reasons. The external lab optimizer supplies policy; a native association demonstrates the stack’s response, not autonomous controller policy or certification. More clients or changing presence does not by itself constitute a controlled channel-utilization/BSS Load test.

Restore default 20 restores default positions and presence without restarting containers. Normal server/appliance startup still uses the default 20-client world; a browser selection is not saved as the boot profile. Closing the tab leaves the server's current room running.

The fixed client pool does not dictate backhaul behavior. Ordinary rooms default to Fixed backhaul · client profiling: startup AP-to-AP RF stays protected while client RF follows geometry. The three backhaul-* rooms declare backhaul_rf: "geometry": loading, Play and dragging apply AP-to-AP geometry too. Their policy card says Geometry-driven backhaul · native parent selection. This does not force parent changes or enable the external parent planner. Weak uplinks may interrupt metrics, controller connectivity and traffic. An explicitly configured assisted server is labeled separately; a disconnected preview cannot prove native behavior.

Switching back to an ordinary room restores the saved fixed RF baseline and verifies the medium values. Then verify actual native association, fresh topology and gateway traffic: RF restoration alone does not prove recovery or force the original star. Fronthaul-disable controls remain separate from backhaul isolation. Clients are gracefully disconnected before client-presence RF isolation, and interrupted supplicant pauses are covered by the recovery journal.

Three short backhaul scenarios: backhaul-branch-formation moves two extenders toward relay opportunities behind a partition; backhaul-parent-handover moves an extender between upper and lower relay coverage; backhaul-isolation-recovery takes an extender and its nearby client behind an isolation wall. Each has ten clients, a 24-second script and a pause at 12 seconds. Inspect applied RF, actual uplink BSSID, both views and gateway traffic, then resume to return by 22 seconds. Native parent selection may fail to adapt; record that rather than interpreting the predicted link as a successful handover. Strong local fronthaul during isolation does not imply end-to-end connectivity.

Live switches apply the world's initial frame and start paused. Press Play to advance scripted positions and presence in the actual lab. All existing mesh roles, role identities, SSIDs and bands are retained. Uploads are limited to 4 MiB and must reference a matching installed layout; unknown roles, extra capacity and unsupported layouts are rejected before RF changes. All viewers receive the same accepted world through the live event stream.

Agent-1 represents the gateway's co-located agent/radios. Extender names follow the controller's current identity mapping; underlying role names and permanent radio identities provide stable bindings even when discovery order changes.

Signal meters: both views use ten segments, filling from the bottom: three red, four yellow, then three green. Unlit upper segments are grey; missing or stale measurements show all grey, not a fabricated zero. Hover/inspect for exact values. Full strength still includes its red and yellow lower bars.

Live room telemetry continues while the optimizer collects candidates; delayed optimizer snapshots cannot overwrite newer network readings. Room freshness uses server event time plus elapsed browser time, not the browser's wall clock. Controller readings older than ten seconds can be supplemented by a successful Wi-Fi ping and matching client-kernel BSSID/band/RSSI measurement; these checks are cached for at most ten seconds per client and RF epoch. The card and inspector identify Client Wi-Fi measurement versus Controller telemetry. No geometry prediction becomes a measured value. Lost telemetry still ages out to grey after 20 seconds. The native controller UI can remain grey when only the room's explicitly identified kernel measurement is available.

Extenders use warm orange-red, distinct from the red controller and client body colors. Cyan marks the selected traffic probe; yellow marks optimizer focus. Both rings can appear on the same client.

The shared RSSI scale advances in 5 dB steps: −85 dBm lights two bars, −70 dBm five, −55 dBm eight, and −45 dBm all ten. Live room bars use controller RSSI in dBm. Offline modeled SNR uses this wmediumd lab's −91 dBm noise floor for the same scale: 24 dB SNR corresponds to −67 dBm and five bars. This conversion is specific to the simulator, not an assumption about physical radios. Modeled link/table colors follow the highest lit segment. Live stale/unknown bars never substitute a model prediction.

4. Camera, playback, and overlays

Opt-in RF scenarios: traffic-low-high-off and traffic-quieter-ap offer 1 then 8 UDP Mbps with 1200-byte datagrams over an existing client's wlan0 during 5–10 and 10–23 seconds. The first five and last seven seconds have no experimental traffic; setup and result collection consume part of each active phase. Existing ICMP profiles remain supported unchanged. Guest-host iperf3, root namespace access, a private configured gateway address on its LAN bridge, and free dedicated TCP/UDP port 55204 are required. RDK also requires guest-host iptables-legacy for temporary source/destination/port-scoped INPUT allowances; older iperf versions without device binding use temporary client OUTPUT guards. The runtime removes only its own rules and processes. UDP live qualification is pending. The inspector separates requested rate, measured sender actual, receiver goodput/loss, and explicit missing or cancelled records. No extra container, radio retune or automatic policy switch occurs. The default same-channel setup is a negative control for load balancing; a positive quieter-channel comparison requires operator preparation and the explicit native-load policy. Pause, lease loss, source offline, world changes and shutdown stop experimental traffic; ordinary beacons and probes continue. Offered rate never supplies native utilization, demand or capacity.

received-same-band-roam and received-discovery-recovery opt selected clients into fresh AP-to-client passive scans on 5 GHz. At their checkpoints, inspect scan identity/age, missing targets and actual BSSID in both views. These clients do not fall back to HAL-matrix candidates or gain a band preference. Missing serving reception pauses steering. Other clients retain their ordinary policy. These new scenarios require live qualification; the room guide describes expectations, not recorded passes.

5. Move a client

  1. Select a private or IoT client; no mode switch is needed.
  2. Drag it across the floor. The ghost is a browser preview; inspect the predicted path and walls before accepting the point.
  3. Release the pointer. In live mode, the server validates and quantizes the position to the room's 5 cm grid.
  4. Wait for the accepted position/RF event. Only then is the solid role authoritative.
  5. Watch the serving measurement and actual association. A new modeled strongest AP can appear before the client has roamed.

One client movement can update up to 30 directed frequency-qualified values: five APs × three bands × two directions. Changed values are applied as one atomic generation and read back before acceptance. A geometrical move that leaves every rounded SNR unchanged is an RF no-op and need not increment the medium generation.

Private and hidden-IoT clients keep their network identities. Body/cohort color and the signal gauge serve different purposes; a blue private client is not an indication of weak RF. The word “static” in a role name describes its base scenario, not a ban on moving it interactively.

A movement is an RF stimulus. It does not directly assign the client to an AP. Scanning, association, controller telemetry, and authorized steering still determine the real network result.

6. Walk to a destination

  1. Choose 0.6 m/s stroll, 1.4 m/s walk, or 3.0 m/s run.
  2. Select a movable role, then select Move to…, or right-click and choose Move to destination….
  3. Click the destination on the floor. The path and marker show the intended motion.
  4. In live mode, use Pause walk, Resume walk, or Cancel walk. Cancel leaves the role at its last accepted position.

The live server owns movement timing and accepted RF steps. Browser frame rate does not determine the RF trajectory. Continued control still depends on the lease: losing or releasing it cancels the walk and retains the last accepted position.

A walk follows the implemented destination path; it is not a navigation or obstacle-avoidance simulator. Walls contribute RF loss where paths cross them. Stop moving and let the room settle when you want a clean optimizer comparison.

In NO CONNECT mode, movement is browser-local. Live pause/cancel and recording controls can be unavailable there. A preview path does not prove any Wi-Fi traffic or association event occurred.

7. Move Agent-1 or an extender

Agent-1 and all four extenders accept the same drag and destination controls as clients. Move the gateway marker to reposition the co-located Agent-1 radios in the RF room.

Ordinary rooms protect startup mesh RF while applying client-serving RF and room presence. The three backhaul-* rooms instead apply geometry-driven backhaul RF on load, Play and drag; native prplMesh chooses parents. Returning to an ordinary room restores the protected RF baseline. The RDK-only adaptive OneWifi parent selector is not installed here. Moving an extender therefore does not promise a new mesh parent; the displayed actual parent always comes from prplMesh NBAPI. Native-observation sessions may explicitly enable --mode stimulus --profiling --model-backhaul to apply mesh RF without external parent selection.

Coordinates do not relocate the controller process, WAN, management interface, or container. The node keeps its permanent identity. Agent-1 stays present; its presence control is protected.

The panel's Actual parent is controller evidence. Strongest simulated peer and the thin dashed floor line preview geometry on the selected band; dragging updates that preview without committing RF until release. Adaptive selection uses verified applied 5 GHz RF and actual Wi-Fi parent associations, not this preview. After 10 seconds without movement, the lab may choose a better loop-free route to Agent-1. A stronger immediate neighbor is not necessarily a better route: its upstream bottleneck and extra hops matter. Simulated strongest-peer links can be reciprocal; they are not a proposed loop-free tree or a steering command. In live mode, disabling a peer's fronthaul does not remove its mesh-peer preview.

The default centered room correctly favors a star: each direct Agent-1 link is 24 dB, while Extender-1 ↔ Extender-3 and Extender-2 ↔ Extender-4 are 23 dB. With the current weakest-link/extra-hop heuristic, either two-hop alternative scores 20 versus 24 direct. A branch or chain needs stronger relay routes relative to the direct paths, not just a visually nearby extender. Moving Agent-1 toward one end of a corridor can produce that geometry; no forced star constraint exists in the external lab planner.

Lab backhaul in Whole lab and Recent events report selection, verification, retry or pause. On an explicitly assisted RDK lab this is OneWifi BSSID control (not installed on prplMesh), not the client AUTO BTM optimizer or native controller backhaul steering. It changes one parent at a time, verifies association and gateway traffic, and restores the previous parent on failure. Controller topology can lag the verified Wi-Fi change. Three failures pause automatic backhaul until the room service restarts. No extra containers or services are needed.

For the centered comparison, leave Agent-1 near the room's middle and position extenders around it. The WebUI's star layout similarly centers Agent-1 and packs extenders around it; its diagram is a logical layout and does not copy exact floor coordinates. Real branch and chain parentage remain visible as reported by the controller.

8. Disappear, disable, and restore

Temporarily disconnect a client

Select the client and choose Disappear. The updated server gracefully disconnects its Wi-Fi session, pauses reconnection and applies minimum SNR to all 30 serving-link values. The container and radio identity remain intact. The marker stays selectable in an absent/hollow style; you can reposition it while absent. The topology removes the actual association after controller convergence, rather than simply hiding a connected client.

To bring it back, select the same marker or its role menu and choose Reappear. RF is recomputed at its current position; normal discovery and association then recover.

Temporarily disable an extender

  1. Select the extender, for example Extender-4.
  2. Choose Disable fronthaul. All its client-serving links are attenuated together, up to 120 values.
  3. Keep watching actual associations while the optimizer measures and evacuates affected clients.
  4. To restore it, click the same grey extender and choose Restore fronthaul in the sidebar or right-click menu.
  5. Wait for measured convergence. Clients return only when that AP is the better eligible choice.

A disabled extender can still be moved. Its fronthaul stays disabled until restored, at which point the current geometry is used. Reset role restores both its session-start position and presence.

Disable fronthaul leaves the extender's agent, container, and backhaul running. It is not a hardware power-off test. Current presence controls use minimum-SNR attenuation (normally −20 dB), not an independent radio-unavailable primitive; actual delivery and disconnection outcomes must be observed.

Optimizer progress and per-client decisions

Topology: Follow room layout continuously follows committed mesh coordinates during dragging and playback, projected using the room's default camera angle so left/right and near/far extenders match that view. Readable spacing may separate nearby groups; this is not a perspective copy. Controller stays beside Agent-1; clients remain around their actual serving AP. Moving a topology mesh icon switches to manual layout, never moves a radio; check the box to resume following. Missing/stale room data retains the last layout and marks the room name as last observed. Hover over the checkbox for follow status. The room name shares the existing topology header without a separate row. Manually orbiting the room camera remains browser-local and does not rotate the topology.

Roaming highlights show a dashed old-position marker, FROM label and arrow to the already-updated client. Teal indicates a matching accepted BTM request, pink an explicitly reported non-BTM move, and grey an unknown method. Missing BTM evidence is not proof of non-BTM. Highlights expire within six seconds, including same-AP band changes; no animation delays association updates or the real roam.

Look for the large green ✓ CONVERGED card over the room, also repeated beside Play. This is continuous, not just a startup check. Green requires fresh optimizer, topology and health evidence, the exact room client/node counts, no pending moves, and all clients meeting the configured AP/band policy for the current RF state. Yellow means moving, settling or converging; grey means measurements are missing/stale or the view is only a preview/replay; red means a lab/mesh failure or blocked steering. Pause at a checkpoint and wait for green before comparing or continuing. Routine background reads do not replace a valid green result. The fixed-size card remains visible in full screen and states its meaning in text, not color alone. Green is not proof of optimal backhaul parent selection or every link's traffic; use the topology and traffic probes for those checks.

The main optimizer status describes the latest valid result rather than every background task. Converged stays steady during routine reading and candidate collection while that result is fresh; it refers to the last evaluation, not a guarantee about unmeasured changes. New non-converged results, measurement failures, degraded health, RF invalidation, and evaluations older than 60 seconds remove the convergence indication immediately. No telemetry or steering is delayed to quiet the display.

Expand Background measurement details to see reading current connections, measuring AP alternatives, and retry progress. This section stays closed until you choose to open it, so routine collection does not flash the main headline. Candidate progress counts completed protocol queries, not guessed percentages; a failed query is not counted as complete. The previous evaluation age and cycle duration remain visible during the next measurement cycle.

Optimizer activity, metrics, expanded measurement details and per-client decisions, and Recent events use fixed-height reading areas, so live updates do not move the controls below them. Scroll inside an area for longer messages or more clients; no error text is truncated. You can also Tab into an area and use the arrow keys, Page Down, or Space to scroll without starting playback. Opening or closing details intentionally changes the panel height. Live updates continue at their normal rate.

Select a station to see its own decision in the optimizer panel. Expand Per-client decisions for every client's serving AP, nominated target, current signal, reported association age, and reason for waiting or moving. Wait values are the remaining time at the last evaluation, not a promise that stale evidence will become valid after a browser countdown. A zero association age persisting beyond a cycle is a reporting problem to investigate.

Incomplete check is not convergence. Missing/stale candidate readings do not prove there is no stronger AP. Moving a device invalidates old convergence and per-client decisions until new evidence is collected. AP names match the controller and topology drawing; internal room role numbers can differ from discovery-order extender labels.

SNR is a ratio in dB; RSSI is received power in dBm. They cannot be compared as equal numbers. A valid RCPI in the normal 0–220 range converts to dBm using RCPI / 2 − 110; for example, RCPI 106 corresponds to −57 dBm. Unavailable values remain unknown, not zero signal.

A band-selector change can alter the model's strongest path without changing the client's actual band. Likewise, a healthy signal says nothing by itself about traffic delivery, available airtime, or physical-radio calibration.

10. Optimizer behavior and recovery time

The authority is chosen when the server starts. Stimulus applies room RF without optimizer work; recommend explains possible steers; act permits bounded automatic BTM requests. The browser's control lease authorizes room edits, not a change of optimizer authority.

Topology automatically tightens the space between AP groups using their visible bubbles and label clearance, then fills the available pane with only a six-pixel margin. The uniform spacing adjustment preserves orientation. Optimize Layout applies the same tightening to a manual arrangement. Neither resizing nor packing changes radio coordinates, associations or steering timing.

Profiling authority: read the fullscreen label

The rev150 prplMesh appliance at ports 18891 (room) and 8091 (topology) runs Unassisted BTM: the external room threshold policy chooses requests, but no RF steering assist, kernel signal fallback, scan-cache refresh or topology animation delay is used to improve the result. This is not the prplMesh controller's autonomous optimization policy. Ready clients can progress while another client is missing; the whole room remains unconverged until membership and fresh measurements are complete.

Native observation means the room issues no client steering requests and performs no candidate collection. Serving-state observation and the selected traffic probe continue. Native stack behavior and client-initiated roaming are observed, not assumed to be a native optimizer. This mode is selected with --mode stimulus --profiling. Neither opening a browser nor acquiring its lease changes that authority.

Profiling normally protects the startup mesh RF and does not choose backhaul parents. To study real modeled AP-to-AP RF without an external parent selector, the operator can add --model-backhaul to stimulus profiling. Weak backhaul may disconnect an extender. Read the authority and backhaul labels rather than assuming all servers run the assisted/adaptive demonstration described below.

Interactive act mode measures eligible private and IoT clients, prioritizing all recently moved clients and clients of a moved AP before returning to the fleet. Candidates remain within each client's SSID and band. The fast interactive policy requires a measured two-dB advantage (four RCPI units), without a pre-action hold or minimum association dwell. Five seconds of post-success cooldown limits repeated moves. Exact ties do not cause a roam.

  1. The server accepts and verifies the new RF generation.
  2. It can evaluate while Play is active, but abandons any measurement spanning different RF generations.
  3. It obtains fresh serving and candidate telemetry under a consistent room state.
  4. The policy evaluates eligible clients. The default batch selects up to eight, weakest serving link first, using gain as a tie-breaker. Visual highlights do not delay the request.
  5. Assisted BTM actions serialize their temporary RF ownership. Unassisted profiling can submit a bounded group of independent client requests; each retains its own verification.
  6. A room change, failed request, or failed verification stops the batch; a later valid cycle evaluates the remaining work.

The assisted hwsim demonstration briefly applies a declared RF steering assist after the measured target is chosen, refreshes candidate scan records, and sends a real EasyMesh/802.11v BTM request. It restores the authoritative room matrix afterward. Assisted values are not fresh optimizer input. Profiling disables this assistance. See the authority label, assist events and individual verification results in the evidence.

Why do clients take time to turn green?

The optimizer's stable badge is green when the last evaluated client has a fresh, normal stay decision; it does not guarantee maximum signal. AUTO BTM is green when automatic BSS Transition Management is enabled and ready, not necessarily executing a roam. Waiting or blocked states use yellow; missing, stale, or RF-invalidated evaluations use grey. Hover over the badges for their meaning.

Movement, telemetry freshness, candidate collection, scans, BTM, reassociation, and traffic checks take time. Several clients may need multiple batches. Native topology visibility is checked immediately and may take up to forty seconds; this is a failure deadline, not a fixed sleep. Full-fleet native metrics retries can still take minutes. Neither the five-second normal polling interval nor a completed drag promises five-second convergence; a new RF epoch wakes polling early.

Watch Fleet check, Stronger AP available, the current focus, and successful verifications. Continued dragging invalidates measurement windows, so a stable room is the fastest way to obtain a useful result.

“Converged” means no stronger eligible measured AP remains for the checked fleet. It does not guarantee every client is green: a client can be on its best AP and still have weak RF because all available paths are poor.

Outside profiling, the fixed-pool interactive optimizer can use a client-kernel RSSI reading after a successful Wi-Fi traffic probe, only when its BSSID and band match the controller. Kernel signal fallback shows how many clients used that explicit measurement source. Profiling does not use that fallback. No modeled signal is substituted and no controller value is overwritten; missing or stale measurements remain visible and cannot establish fleet convergence.

Interactive evidence is retained in a bounded journal. Long runs may expire their beginning; an expired live cursor resynchronizes, but full replay refuses an incomplete history. Evidence queue or disk failures mark qualification incomplete without pausing RF control. The operator can inspect /api/demo/storage for queue, retention and failure status. Archive completed runs separately; per-run rotation does not delete old run directories.

Interactive act mode has no default lifetime cap. It permits up to 300 requests per rolling minute, with at least five seconds between requests to the same client. A full window retries automatically. Three consecutive terminal failures within 180 seconds pause only that client; a fourth alternating AP reversal within 60 seconds under unchanged RF is blocked. Other clients and measurements continue.

Use Resume steering beside External optimizer to clear these client pauses without restarting or resetting positions, presence, playback or RF. Request counters, cooldowns and the rolling window are retained. Relevant RF changes also clear obsolete client protection history. An explicit --max-actions N still bounds deliberately finite runs and is not bypassed by Resume.

11. Reset and shared control

Reset role returns a live role to its session-start position and presence. Reset all applies those resets to changed controllable roles. These are regular RF transactions, so expect new measurement and convergence work afterward.

In the static sandbox, reset clears local overrides and returns to the base scenario at the current playback time. Reset is not an arbitrary undo history and does not restart the lab.

One browser owns the renewable control lease; other browsers can observe. A competing operator receives a lease conflict. Coordinate control or wait for the existing lease to expire instead of repeatedly submitting edits. The normal lease is 30 seconds and renews while control remains active.

Closing the tab or switching out of interactive control releases or eventually expires the lease. The server retains accepted room state; it does not undo the presentation. Accepted walks are cancelled when the lease is lost. Reopen the current run, inspect the authoritative state, and acquire control again before editing.

Stopping the room process is different: it restores the exact captured pre-run RF baseline. There is currently no viewer button that performs this operator shutdown.

12. Recording and replay

  1. In interactive live mode, select Start recording and give the recording a name.
  2. Move clients or mesh nodes, run destination walks, and change presence as usual.
  3. Select Stop recording.
  4. Select Download world to save the compiled JSON.
  5. Open that file through the viewer's local-world input to inspect its geometry and timing without a lab.

Only accepted server positions and presence changes are recorded. Unaccepted ghosts are not part of the recording. The exported wmdcfg.world-plan.v1 includes bound roles, timed positions, presence intervals, and calculated links. Geometry samples are compiled at the recording cadence, currently 200 ms.

A recorded world reproduces stimulus; it does not guarantee identical Wi-Fi scheduler timing or client choices on a later live run. Full evidence replay uses the run directory, which also contains controller and optimizer events.

Recording is unavailable in NO CONNECT mode. Local-world loading and playback remain available. Closing the browser is not the same as stopping a recording; use Stop recording before Download world.

13. Three short demonstrations

A. Walk one client between rooms

  1. Start from a healthy, stable fleet and note a client's actual AP and signal.
  2. Move it toward another extender using 1.4 m/s.
  3. Compare predicted best path with the actual association line.
  4. Stop at the destination and watch measurement, recommendation, BTM, and verification events.
  5. Reset the role and observe the return; save the recording if needed.

B. Disable Extender-4, then restore it

  1. Note its serving clients and select Disable fronthaul.
  2. Leave the room stable while clients evacuate through normal steering.
  3. Select the same grey extender and choose Restore fronthaul.
  4. Observe which clients return because it is their best eligible AP. Others may correctly stay where they are.
  5. Check fleet coverage, traffic, and health, not just marker colors.

C. Swap two extenders

  1. Note the initial positions of Extender-3 and Extender-4.
  2. Drag each to the other's position, completing both edits.
  3. Stop editing. Expect measurement work to restart for the changed environment.
  4. Follow client ownership and actual backhaul separately; a room coordinate is not a topology assignment.
  5. Use Reset role on both extenders, or Reset all if every edit should return to the session baseline.

In the public sandbox these demonstrations illustrate geometry only. Present a successful live steer only when its real controller and verification evidence is available.

15. Operator setup and shutdown

Run these commands inside the prplMesh appliance, from its checked-out repository. The 0908 appliance is prplmesh-20-0908 on rev150, using canonical branch codex/0908-clean. Other hosts retain their separately deployed release. The commands below require shell access; the public website does not run them.

systemctl stop prplmesh-room-demo.service
cd /opt/prplmesh-lab
prplmesh-lab-start status
demo/room-demo check
demo/room-demo interactive --mode recommend --listen 0.0.0.0:8891

For an explicitly authorized automatic-steering session:

demo/room-demo interactive \
  --mode act --yes-act --profiling --steering-rate-limit 300 \
  --listen 0.0.0.0:8891

The rev150 0908 proxy maps outer port 18891 to appliance port 8891. Do not create a second room process on the same medium. A process PID or a reachable page alone is not a complete medium-health check.

The updated CLI creates no operator token file. Interactive control requires only the renewable lease and normal revision checks. Restrict network access to trusted users or place an authenticated gateway in front of the whole service.

Normal stop

Use Ctrl + C in the owning room terminal, or stop the actual owning service if the operator launched one. SIGINT/SIGTERM drain accepted work and restore the captured RF matrix. Check the final outcome and restored=true; a worker failure can have outcome=failed even if RF restoration succeeded.

After an unclean interruption

demo/room-demo recover

This uses the checksummed journal at /run/prplmesh-room-demo/recovery.json. Recovery refuses an unexpected medium instance or unexplained generation. Resolve that condition before starting another writer. Do not run another configurator, independent RF-bias helper, or room scenario concurrently.

Replay a completed run

demo/room-demo replay \
  /var/lib/prplmesh-lab/room-runs/RUN_ID \
  --listen 0.0.0.0:8891

Open /viewer/ on that replay server and ensure port 8891 is free first. Explicit ?mode=replay bookmarks still work. Replay serves saved evidence and is not an interactive live session.

The installed service stores evidence under /var/lib/prplmesh-lab/room-runs/RUN_ID/; manual CLI runs default to /tmp/prplmesh-room-demo-runs/. Copy important runs before rebuilding the appliance.

  • world.json, layout.json, and runtime-world.json: scenario inputs and viewer geometry.
  • inventory.json, bindings.json, and demo-manifest.json: identities and run configuration.
  • live-events.jsonl: accepted commands, RF generations, network observations, optimizer actions, traffic, and restoration.
  • health-preflight.json, health-postflight.json, and interactive-summary.json: acceptance and final outcome.
  • recovery.json: the final checksummed medium-recovery state.
  • recorded-mobility.json and recorded-world.json: recording outputs, when present.
  • evidence-index.json: artifact sizes and SHA-256 digests.

Mutation contract

The browser normally handles this. Mutations require a same-origin request, the acquired lease token and a unique command ID; no operator token is required. Position/presence/movement writes carry the latest expected_revision and If-Match: "world-revision-N".

Acquire control with POST /api/demo/interactions/lease. Position uses PUT /api/demo/roles/ROLE/position; presence uses PUT /api/demo/roles/ROLE/presence. A position body has this shape:

{
  "token": "LEASE_TOKEN",
  "expected_revision": 4,
  "client_sequence": 1,
  "command_id": "manual-example-position-1",
  "position": [12.5, 8.0],
  "final": true
}

This is an example, not a ready-to-send current command. Re-read the revision and substitute a current lease. Retrying the exact same command ID and body returns its original result without a second RF update; changing that body's meaning under the same ID conflicts.

Keep three identifiers distinct: event sequence orders evidence; room revision guards accepted world changes; medium generation identifies RF state. A temporary steering assist or RF no-op means these counters need not advance together.

17. Glossary and current limits

AP / agent / extender
An access point serves clients; an EasyMesh agent manages its radios. An extender is a mesh node with an upstream backhaul connection.
Fronthaul / backhaul
Fronthaul connects client stations to APs. Backhaul connects mesh nodes toward the gateway.
STA / SSID / BSSID
A station is a Wi-Fi client. An SSID names its network; a BSSID identifies an individual AP service endpoint.
BTM
802.11v BSS Transition Management: the protocol used to request a client move to another BSS.
Golden World
A deterministic geometry and RF-stimulus plan used for repeatable experiments.
hwsim / wmediumd
Linux virtual radios and a userspace wireless medium. Real Wi-Fi and EasyMesh software runs over controlled virtual RF conditions.
Room revision / environment epoch
Versioning for accepted room state and its RF environment. Movement can invalidate a candidate measurement window.
Control lease
A renewable lease selects the current interactive owner and prevents competing browser writes. It is a concurrency safeguard, not user authentication.

Supported here: client and mesh-node movement, bounded fronthaul absence/restoration, live measurements, sequential verified fleet steering, accepted-state recording, and evidence replay.

Wall/door editing, calibrated interference regions, arbitrary undo history, per-role simultaneous browser ownership, and physical-radio prediction are not provided by these controls. A deterministic stimulus is not a guarantee of identical live timing.

The lab demonstrates protocol and policy behavior under controlled virtual conditions. Candidate measurement provenance, modeled attenuation, traffic evidence, and infrastructure failures remain separate facts.
